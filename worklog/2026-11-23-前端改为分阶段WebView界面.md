# 前端改为分阶段 WebView 界面

## 做了什么

- 把 Tkinter 单屏界面换成三屏：开始（拖放 + 选项）→ 处理中（大状态 + 进度 + 绿盾等待卡）→ 交付与清理（交付卡 + Word 清单）。左侧侧栏始终显示五步进度。视觉为 macOS 极简风：白底、浅灰侧栏、系统蓝。
- 前后端分离：`web/` 是纯静态前端，`web_app.py` 用 pywebview（Edge WebView2）承载窗口并暴露 JS API，`app_controller.py` 是从原 `desktop_app.py` 抽出来的、与界面无关的调度层，按快照推送状态。
- `pdf_workflow.py`、`archive_input.py`、`local_services.py`、`wps_worker.py` 一行未改。旧界面保留，可用 `--classic` 启动；缺少 pywebview 时自动退回。

## 为什么

原界面把所有按钮、表格、日志一直摆在同一屏，用户每一步只需要做一件事，却要在一堆灰按钮里找。按阶段只显示当前需要的东西，"继续等待解密""确认清理"只在该出现的时候出现。

## 决策与坑

- 设计过程：先让 Codex 出了 9 版换皮稿，用户都不满意——问题在结构，不在配色。第二轮分成两个方向：保留 macOS 版布局只换配色，和按阶段分屏。最后定为分阶段结构 + macOS 极简配色，先在 Claude Design 画布上定稿再写代码。
- 本机 Chrome 会死机，所以用 pywebview 的 edgechromium 后端，不开外部浏览器。
- 拖放的真实路径在 Python 侧读取（DOM drop 事件里的 `pywebviewFullPath`），JS 只负责高亮和阻止默认行为。拖入文件夹已在 WebView2 上按 API 接好，但还没有人工实拖验证。
- 后端事件来自工作线程，`StatePusher` 把短时间内的多次更新合并成一次 `evaluate_js`，避免 WPS 逐份导出时刷屏卡顿。
- 关闭窗口时如果任务在跑，`closing` 事件返回 False 拦下，并在页面里提示先停止。
- `web/app.js` 支持 `?demo=start|process|waiting|error|review`，可以在普通浏览器里预览各状态，不需要 WPS。
- `tests/test_wps_batch.py` 在没装 pywin32 的环境里本来就会报错，不是本次引入。

## 一句话亮点

后端零改动：同一个 Workflow，前端从 Tk 换成 WebView 三屏，靠一层 Controller 把"事件队列 + 按钮状态"变成一份 JSON 快照。
